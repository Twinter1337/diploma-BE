## Architecture

**Clean Architecture — 4 logical layers** (currently a single `.csproj`; split into separate projects as implementation grows):

```
Domain       → Entities (EF, db-first), Enums, Models (clean POCOs), Interfaces
Application  → Models/Dtos, AutoMapper profiles, Services (depends on Domain only)
Infrastructure → AppDbContext + Repositories, Stripe, Azure Blob, Redis, SMTP, BackgroundService
API          → Controllers, Program.cs
```

**Dependency rule is strict:** Application services call only Domain interfaces — never EF Core, Stripe, or Azure SDKs directly.

---

## Data Flow

```
DB → Entity (EF scaffold) → Model (service layer) → DTO (API response)
DTO (API request) → Model → Entity → DB
```

- **Entities** (`Entities/`) — generated by `dotnet ef dbcontext scaffold`; never modify by hand; use `short` for enum columns
- **Models** (`Models/`) — clean POCOs with typed enums; used in all service and business logic code
- **DTOs** (`Models/Dtos/`) — API input/output; organized by feature subfolder (Auth, Users, Trainers, Clients, Documents, Tags, Schedule, Bookings, Payments, Reviews, Notes, Notifications, Achievements, Tickets)
- **Enums** (`Enums/`) — all enums typed as `short`; map directly to DB `SMALLINT` columns

## Key Patterns

### Repository + Unit of Work
- Each aggregate root has a typed repository (`IUserRepository`, `IBookingRepository`, etc.)
- `IUnitOfWork.SaveChangesAsync()` wraps multi-repository operations in one transaction (critical for booking creation and cancellation)

### AutoMapper
- Entity → Model and Model → DTO mappings defined as AutoMapper profiles per feature in the Application layer
- Domain entities (EF) never leave the repository layer — services always work with Models

### Dependency Injection lifetimes
- `AppDbContext`, Repositories, Application services → `Scoped`
- Redis `IConnectionMultiplexer` → `Singleton`
- `NotificationBackgroundService` → `Singleton` (registered as `IHostedService`)

## Database (PostgreSQL)

- **DB-first**: schema lives in PostgreSQL; entities are scaffolded, never written by hand
- All PKs are `UUID` via `gen_random_uuid()`
- Soft delete: set `is_active = false` on users; no hard deletes on `bookings` or `schedule_slots`
- Enums stored as `SMALLINT`; typed enum classes live in `Enums/`
- `AppDbContext` lives in `Repositories/AppDbContext.cs` (namespace `CaoachlyBE.Repositories`)
- Connection string config key: `ConnectionStrings:Postgres`

**Two PostgreSQL triggers (do not replicate in C#):**
1. `recalculate_trainer_rating` — fires on `reviews` INSERT/UPDATE/DELETE; keeps `trainer_info.rating` and `reviews_count` accurate
2. `update_slot_status` — fires on `bookings` INSERT/UPDATE; sets slot to `Available/Booked/SoldOut` based on active booking count vs `max_clients`

## Critical Business Logic Locations

| Concern | Where |
|---|---|
| Booking creation | `BookingService` → validate slot available → conflict check → create booking → Stripe Checkout session → return URL |
| Stripe webhook | `StripeWebhookController` → verify signature → `checkout.session.completed` → confirm booking + payment atomically via UoW |
| Cancellation + refund | `BookingService.CancelAsync` → determine initiator from JWT role → calculate refund (100% if trainer; >24h client = 100%, ≤24h = 50%) → Stripe Refund API → update booking + payment |
| Session reminders | `NotificationBackgroundService` — runs every 10 min; queries `bookings JOIN schedule_slots` where `ABS(start_time - NOW() - reminder_minutes) < 1 min`; prevents double-send by design (window passes after 10 min) |
| Achievement check | Called after `booking.status → 3` (completed); checks completed sessions count, distinct trainers, distinct specialization tags against achievements catalog |

## Redis Cache

- Used exclusively for trainer search results
- Key pattern: `trainers:search:{md5_of_query_params}`
- TTL: configurable via `Cache:TrainerSearchTtlSeconds` (default 300s)
- **Invalidate on:** trainer profile update, slot create/delete, tag update

---

## Authentication

- JWT access token (15 min) — payload includes `sub`, `role`, `email`
- Refresh token stored **hashed (SHA-256)** in `refresh_tokens` table; rotation on every refresh
- Password reset tokens stored in `password_reset_tokens` with expiry + `used_at`
- Role-based: `[Authorize(Roles = "Trainer")]`, `[Authorize(Roles = "Admin")]`
